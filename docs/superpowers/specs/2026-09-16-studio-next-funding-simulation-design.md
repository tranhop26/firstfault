# Studio Next funding simulation compatibility design

## Problem

`prepare_funding` accepts an expiry only when it is later than the transaction timestamp and no more than one hour ahead. The production frontend computes a 15-minute expiry from the browser clock, then asks `genlayer-js@2.0.0-rc.1` to estimate fees before submission.

Studio Next's simulated write omits the GenVM transaction datetime. The current Studio implementation therefore supplies its historical fallback datetime (`2024-11-26T06:42:42.424242Z`). A 2026 browser expiry is more than one hour after that fallback, so fee estimation fails with `Invalid funding intent expiry` before the wallet can approve the real transaction.

The same simulated request succeeds when retried with `sim_config.genvm_datetime` set to the current UTC time. The successful simulation returned a recommended maximum fee deposit of `0.000613838400010352 GEN`. No funding transaction was submitted during diagnosis.

Separately, Studio Next reports successful finalized writes as `SUCCESS` in the leader receipt. The frontend's submitted-write check currently accepts only `FINISHED_WITH_RETURN`, which caused the already-successful `create_workflow` transaction to be presented as a failure.

## Selected approach

Implement a narrow frontend compatibility layer without changing or redeploying the frozen Intelligent Contract.

For `prepare_funding`, the contract client will first use the normal SDK fee-estimation path. If and only if Studio returns the decoded contract error `Invalid funding intent expiry`, the client will retry the same encoded simulation request with `sim_config.genvm_datetime` set to the current UTC timestamp. It will normalize Studio's returned recommended fee preset into the existing fee quote shape. All other estimation errors remain failures and must not trigger the fallback.

For finalized writes, the client will treat an accepted or finalized receipt as successful when the existing execution evidence helper finds either `FINISHED_WITH_RETURN` or a leader receipt result of `SUCCESS`. Explicit execution errors remain failures.

## Alternatives considered

1. Wait for a Studio or SDK release that forwards simulation datetime. This avoids application compatibility code but leaves the live hackathon flow blocked for an unknown period.
2. Redeploy a new contract that derives or relaxes funding intent expiry. This changes the frozen source, contract address, deployment evidence, and trust surface for a problem confined to simulation.
3. Skip simulation and use an oversized generic fee preset. This would unblock submission, but it would weaken fee accuracy and require a larger temporary wallet deposit.

The selected approach is preferred because it preserves the deployed contract and continues to show the wallet an estimate derived from the exact call.

## Components and data flow

### Studio error recognition

A small contract-client helper will inspect the SDK/RPC error without relying on the user-facing Viem message. It will decode the receipt's base64 contract result and require an exact match for `Invalid funding intent expiry`. It will also require the original encoded request parameters to be present before allowing the retry.

### Timestamp-aware retry

The retry will reuse the exact request generated by `genlayer-js`, add only:

```json
{
  "sim_config": {
    "genvm_datetime": "2026-09-16T15:29:22.506Z"
  }
}
```

The timestamp shown is an example; the client generates the current UTC ISO timestamp for every retry. It will call Studio's read-only `sim_estimateTransactionFees` method. No signature, wallet prompt, state mutation, or on-chain transaction occurs during either estimation attempt.

### Fee normalization

The compatibility layer will read `receipt.genvm_result.fee_accounting.recommended_fee_preset`, validate the required distribution and fee fields, and convert integer values to `bigint`. Malformed or absent recommendation data will fail closed instead of inventing a fee.

The resulting quote continues through the existing confirmation callback. Submission is allowed only after the user confirms the exact account, chain, contract, value, and maximum fee deposit.

### Receipt success normalization

The submitted-write result check will reuse the existing execution-evidence logic. A receipt must still be accepted or finalized, and its execution evidence must indicate success. This changes presentation and reconciliation only; it does not weaken transaction authorization.

## Error handling and safety

- Retry only the exact known timestamp-expiry simulation failure.
- Never retry wallet rejection, provider mismatch, insufficient balance, invalid state, wrong sender, malformed RPC data, or other contract errors.
- Fail closed when Studio does not return a complete recommended fee preset.
- Keep the 15-minute intent lifetime unchanged for the real transaction.
- Preserve action-time wallet, network, contract, amount, and maximum-fee confirmation.
- Do not reuse the expired workflow for end-to-end proof. After deployment, create a new workflow with fresh deadlines.
- Do not send any live transaction as part of automated tests.

## Tests

Following test-driven development, add failing regression tests before production changes:

1. A `prepare_funding` estimate that fails with the exact expiry error is retried with the same request plus a current `sim_config.genvm_datetime`.
2. The successful retry's recommended preset is converted to the existing fee quote and used for submission.
3. Other simulation errors are propagated without retry.
4. Missing or malformed recommended fee data fails closed.
5. A finalized receipt whose leader execution result is `SUCCESS` is accepted.
6. An explicit execution error is still rejected.

Run the focused contract-client tests first, then the full frontend test suite, type check, and production build.

## Deployment and live verification

After tests pass, deploy only the frontend compatibility change to the existing Vercel project after confirming the active Vercel account/team at action time. Verify the production deployment URL and commit identity.

Then use the connected OKX wallet on Studio Next chain `61997` and the existing contract `0xf7136eDe8ba1761562fEcb2147609F3A2932c449` to create a new workflow. Before each on-chain action, present the exact action and maximum fee for user confirmation. Capture transaction hashes, explorer status, contract readbacks, and visible production state as completion evidence.
